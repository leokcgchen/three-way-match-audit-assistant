# 多单据业务分组与字段证据边界规范

## 目的

将混合上传的合同、订单、发票、出库/签收、回款等单据先分隔为可审计的 `BusinessGroup`，再在**同一组内**进行字段映射、三单匹配和截止性测试。禁止以全任务单据作为LLM上下文，禁止跨组串单。

## 处理顺序

1. OCR/解析逐份产生原始字段、位置和 `_field_meta`。
2. 分组引擎优先使用订单号、合同号、发票号等强主键；人工写入的 `business_group_id` 优先。
3. 弱特征（客户名、金额、日期、摘要）只能形成“待确认依据”，不得静默合并两个业务组。
4. 业务组绑定通过后，才做组内字段一致性；金额差异属于字段一致性问题，不得反向改判为分组冲突。
5. LLM仅收到当前 `group_id` 的 `llm_context_document_ids`，仅生成候选/解释；不能创建、合并、拆分或放行业务组。

## 状态定义

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `MATCHED` | 有可解释强主键，或人为明确调整 | 可进入字段校对；仍可有字段待核 |
| `NEEDS_REVIEW` | 没有足以自动绑定的强证据 | 人工确认、拖拽、拆分或合并后再继续 |
| `CONFLICT` | 业务身份本身相互矛盾 | 阻断后续正式结论，需人工解决 |

`field_consistency_alerts` 不改变分组状态：它提示审计师进入字段一致性矩阵核对。

## 数据契约

```json
{
  "group_id": "SO25-0281",
  "confidence_score": "number in [0, 1]",
  "status": "MATCHED",
  "strong_keys": ["orderNo:SO25-0281", "contractNo:HT25-0281"],
  "source_documents": [{"file_name": "...pdf", "doc_type": "invoice"}],
  "weak_evidence": {"counterparties": ["客户A"], "dates": ["2025-12-20"]},
  "conflicts": [],
  "field_consistency_alerts": [],
  "llm_context_document_ids": ["...pdf"]
}
```

## 字段证据铁律

1. 字段矩阵中只有 `ACCEPTED` 的原文证据值可以显示为正式单元格；没有原文则为空。
2. `normalized_candidate` 或模型输出只能显示为橙色“AI候选”，不得作为匹配、底稿导出或通过结论的输入。
3. 审计师可以直接改值、在原文圈画提取、或将已提取字段重新绑定到字段库；确认动作必须写入HITL轨迹。
4. “组内字段不一致”由三单字段一致性阶段报告原因，不等于“不是同一笔业务”。

## 给LLM的受控提示词（P3）

### LLM判断步骤与工具边界

1. 只读读取 `context_documents` 的OCR文本、页码、坐标和已经接受的字段；不得读取其他业务组、不得调用写入工具。
2. 对每个候选逐项附上 `source_document`、页码、坐标和原文摘录；没有定位证据时输出 `null`/空候选。
3. 输出后执行结构校验：候选文件必须在 `llm_context_document_ids` 内、坐标必须存在、字段名必须是受控字段库字段。
4. 仅人工在界面确认后，后端才可通过既有字段保存API写入 `ACCEPTED`；模型、提示词和候选服务没有写入权限。

```text
角色：你是审计辅助候选生成器，不是裁决者。
任务：仅对 group_id={{group_id}} 的 documents 作语义审阅，并为字段 {{field_key}} 输出候选及原文依据。

输入边界：只能使用 context_documents；不得引用其他业务组、常识补全或假设值。
允许：解释字段标签、附近文字、表格列名和组内勾稽关系；列出候选、置信理由和不确定性。
禁止：写入正式字段、将候选标为已确认、生成不存在于原文的金额/日期/编号、改变业务组归属、输出 PASS/FAIL 审计结论。

输出严格JSON：
{
  "group_id": "...",
  "field_key": "...",
  "candidates": [{"value":"...","source_document":"...","page":0,"bbox":[0,0,0,0],"excerpt":"...","confidence":"number in [0,1]","reason":"..."}],
  "recommended_candidate_id": "...|null",
  "needs_human_review": true,
  "cannot_determine_reason": "...|null"
}
验收：每个候选都要有来源文件和原文摘录；缺少证据时 candidates 为空且 needs_human_review=true。
```

## 人工调整与追溯

- UI中将单据标签拖入另一张业务组卡片即可执行人工调整。
- API：`POST /jobs/{job_id}/business-groups/move-document`。
- 后端写入 `business_group_id` / `business_group_manual`、作废下游字段结果，并记录 `move_business_group_document` HITL事件（前组、后组、时间、理由）。
- 正式底稿需写入 `group_id` / `chain_id`，确保每一行可追回对应单据组。

## 验收案例

- 72份真实PDF混合批次：应分为10组，单据总数72，全部入组。
- 同组金额差异：业务组仍为 `MATCHED`，产生 `field_consistency_alerts`，在字段一致性阶段处理。
- 无强主键的单据：不得自动拼接至多个候选组，应为 `NEEDS_REVIEW`。
- 人工拖拽：重新查询组列表后文件只出现于目标组，并存在HITL记录。
