# 抽样业务联合索引与智能文件归类设计

日期：2026-08-24

## 1. 目标

系统读取凭证文件名及必要的 OCR 字段后，能够利用抽样清单中的业务编号和订单号，把文件稳定归入清单内的固定业务。归类过程必须可解释、可追溯，并且不能因局部数字相似而误合并业务。

## 2. 基本原则

1. `business_id`（业务编号）仍是系统内部唯一、稳定的审计业务主键。
2. 订单号及未来经批准的其他编号作为该业务的索引别名，不替代业务主键。
3. 界面可以把主键和别名组合显示为 `业务编号 & 订单号`，但数据库和匹配引擎保留字段结构，不保存为不可拆分的拼接主键。
4. 文件匹配到业务编号或唯一订单号，都可以归入对应业务。
5. 只出现相似数字时不得自动归类；只能形成待人工确认的候选。
6. OCR 或文件名不能扩充抽样清单。无法唯一归属的文件进入异常区。

## 3. 数据模型

每条抽样业务保存：

```json
{
  "business_id": "YW-2025-3962",
  "order_numbers": ["SO-251209-7214"],
  "index_aliases": [
    {
      "type": "business_id",
      "value": "YW-2025-3962",
      "normalized": "YW20253962",
      "source_column": "业务编号"
    },
    {
      "type": "order_number",
      "value": "SO-251209-7214",
      "normalized": "SO2512097214",
      "source_column": "销售订单号"
    }
  ],
  "display_index": "YW-2025-3962 & SO-251209-7214"
}
```

一条业务可以关联多个订单号。反向索引结构为：

```text
规范化索引值 → {业务编号集合}
```

当一个订单号指向多个业务编号时，该别名被标记为不唯一，不得用于自动归类。

当前样例清单中的 10 个业务编号和 10 个销售订单号均唯一且一一对应，但设计不依赖一对一假设。

## 4. 清单解析

导入抽样清单时：

1. 继续用已实现的自适应规则选择业务主键列。
2. 独立识别订单号列，支持“销售订单号、订单编号、订单号、采购订单号、Order No、Sales Order”等表头。
3. `_parse_sheet_rows` 除 `business_id` 外保留 `order_numbers`，不再丢弃订单号列。
4. 相同业务编号出现多行时，合并其订单号并去重，不因多行拆成多笔业务。
5. 相同订单号对应多个业务编号时，在清单导入结果中记录 `ambiguous_aliases`，前端提示该订单号只能人工裁决。
6. 业务编号为空的行不能仅凭订单号自动创建新的抽样业务。

## 5. 编号规范化

确定性规范化允许：

- 英文字母统一为大写；
- 去除首尾空白；
- 匹配时忽略空格、短横线和下划线差异；
- 仅在编号形态和上下文明确时处理 OCR 常见混淆：`O ↔ 0`、`I/l ↔ 1`；
- 保留原始值用于界面显示和审计轨迹。

禁止：

- 仅抽取末尾若干数字后自动合并；
- 仅凭编辑距离、包含关系或“看起来相似”自动归类；
- 把日期、金额、数量、发票号码中的局部数字当作业务索引。

## 6. 文件名解析

解析器从完整文件名中提取带字母前缀和数字段的编号候选，例如：

```text
YW-2025-3962_销售订单_SO-251209-7214.pdf
```

提取结果：

```text
YW-2025-3962
SO-251209-7214
```

候选首先与清单的业务编号索引和订单号别名索引进行规范化精确匹配。OCR 字段仅作为文件名未提供足够索引时的补充来源。

## 7. 归类决策矩阵

| 检测结果 | 处理方式 | 置信度 |
|---|---|---|
| 业务编号精确匹配唯一业务 | 自动归类 | 高 |
| 唯一订单号精确匹配唯一业务 | 自动归类 | 高 |
| 业务编号与订单号均命中，且指向同一业务 | 自动归类，并记录双证据 | 最高 |
| 文件名精确匹配，OCR 未提取出编号 | 采用文件名结果 | 高 |
| 文件名与 OCR 命中不同业务 | 进入异常区，提示来源冲突 | 冲突 |
| 业务编号与订单号分别指向不同业务 | 进入异常区，提示联合索引冲突 | 冲突 |
| 订单号在清单中对应多个业务 | 进入异常区，要求人工选择 | 歧义 |
| 只有格式规范化后精确匹配 | 自动归类并记录规范化方式 | 高 |
| 仅有相似数字或单字符差异 | 展示候选，不自动归类 | 待人工确认 |
| 未发现任何有效索引 | 进入异常区 | 未归属 |
| 明确识别到清单外同族业务编号 | 进入异常区并推荐删除 | 清单外 |

自动归类必须满足：候选最终只指向一个抽样业务。任何两个强索引指向不同业务时，冲突优先于分数，不允许高分覆盖冲突。

## 8. 相似候选规则

相似匹配仅用于减少审计师搜索成本，不直接改变文件归属：

1. 编号前缀相同；
2. 规范化后长度相同或接近；
3. 最多存在一个 OCR 常见字符混淆或单字符差异；
4. 候选必须来自抽样清单已有索引；
5. 界面同时展示客户、金额、日期等辅助证据，但辅助证据不能把候选自动升级为已归类。

禁止用通用百分比相似度直接自动放行。

## 9. 审计轨迹

每份文件保存：

```json
{
  "sample_business_id": "YW-2025-3962",
  "business_index_source": "filename",
  "business_index_evidence": [
    {
      "type": "business_id",
      "detected": "YW-2025-3962",
      "matched": "YW-2025-3962",
      "source": "filename",
      "match_method": "normalized_exact"
    },
    {
      "type": "order_number",
      "detected": "SO-251209-7214",
      "matched": "SO-251209-7214",
      "source": "filename",
      "match_method": "normalized_exact"
    }
  ],
  "business_index_status": "MATCHED",
  "business_index_confidence": "highest"
}
```

审计师人工选择业务后，状态改为 `MANUAL_MATCHED`，保留原候选、冲突原因、操作时间和人工选择结果。

## 10. 界面设计

### 总工作台

业务行主标题仍显示业务编号，次级索引显示：

```text
联合索引：YW-2025-3962 & SO-251209-7214
```

多个订单号时显示前两个，并提供“查看全部订单号”。

### 上传凭证

每份文件显示：

- `已归类：YW-2025-3962`；
- `命中索引：业务编号 + 订单号`；
- 可展开查看检测值、清单值、来源和规范化方式。

异常区区分：

- 联合索引冲突；
- 订单号重复；
- 仅相似候选；
- 未取得索引；
- 清单外业务。

仅相似候选必须由审计师点击确认，不得默认选中第一项。

## 11. 与序时账及三单匹配的边界

- 序时账关联仍以 `business_id` 为最终查询主键；订单号仅帮助文件归入该业务。
- 订单号继续作为业务内部的三单勾稽字段。
- 一对多签收单和多张发票均挂在同一 `business_id` 下，不因文件数量拆分业务。
- 联合索引只解决“这份文件属于哪笔抽样业务”，不直接决定三单字段是否一致。

## 12. 迁移策略

1. 重新解析现有抽样清单，补充每条业务的 `order_numbers` 和 `index_aliases`。
2. 对已识别文件仅重新执行索引归属，不重跑 OCR。
3. 已有 `sample_business_id` 若与新联合索引一致，保留并补充证据。
4. 已有归属若与订单号别名冲突，移入异常区等待审计师确认，不静默覆盖。
5. 迁移不新增抽样业务，不改变序时账原始数据。

## 13. 验收标准

1. 当前清单能够保留 10 个业务编号与对应的 10 个销售订单号。
2. 只包含 `YW-2025-3962` 的文件能自动归入该业务。
3. 只包含 `SO-251209-7214` 的文件也能自动归入 `YW-2025-3962`。
4. 同时包含正确 YW 和 SO 的文件记录双证据并获得最高置信度。
5. 正确 YW 与属于另一业务的 SO 同时出现时进入异常区。
6. 重复订单号不能自动归类。
7. `YW-2025-3962` 与 `YW-2025-3992` 不会因数字相似而自动合并。
8. `SO 251209 7214` 与 `SO-251209-7214` 可以通过确定性规范化匹配。
9. 现有 33 份文件重新归属时不调用 OCR，并保持 10 笔抽样业务不变。
10. 界面不只显示结论，还能展开查看匹配索引及来源。
11. 不执行任何 Git 写操作。
