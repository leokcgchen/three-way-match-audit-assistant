# 业务行上传后自动审阅与红黄绿分流设计

## 1. 目标与范围

审计师将 PDF/图片拖入某一抽样业务行后，系统立即完成该批文件的业务绑定、OCR、字段提取、三单匹配、一对多累计和截止性测试，随后生成逐笔红黄绿结果。绿灯自动收口；黄灯、红灯进入人工处理。

本次只改造「按业务行上传」的编排和进度展示；混装资料包仍必须由审计师显式勾选，不自动拆包。

## 2. 交互与状态机

每个抽样业务行始终保留在上传页，不再因文件入队或完成识别而从列表消失。业务行状态依次为：

`WAITING_UPLOAD → UPLOADING → OCR_PROCESSING → AUTO_REVIEWING → GREEN / YELLOW / RED`

- `UPLOADING`：文件正在落盘，不可重复提交同名文件。
- `OCR_PROCESSING`：展示已处理页数/文件数，允许切换页面。
- `AUTO_REVIEWING`：显示「正在执行三单匹配与截止性测试」。
- `GREEN`：证据门禁、必要字段及规则测试均通过，自动确认结论。
- `YELLOW`：类型存疑、绑定歧义或需要专业判断，不自动放行。
- `RED`：缺单据、缺关键字段、金额歧义、三单冲突或截止性异常，必须处理。

上传后不再自动切换到「待处理」标签，而是在原业务行上持续展示处理状态。审阅完成后进入总工作台：绿灯默认收起，黄灯和红灯置顶。

## 3. 数据流与规则边界

1. 前端通过 `business_hints` 把文件与目标抽样业务绑定，上传成功后立即对本批文件调用 `/process`。
2. OCR 和字段提取完成后，后端沿用 `finish_after_classify`，只对当前受影响业务执行证据串联、一对多累计、三单匹配和截止性测试。
3. 业务行上传是审计师给出的归属上下文，但最终分类、字段和匹配主张仍必须保留页码、文本和坐标证据；文件名或模型分数不能单独放行。
4. 红黄绿以 `/chains` 的逐笔结果为唯一口径。左侧阶段进度与顶部汇总不再读取多笔任务的顶层镜像字段，而是读取逐笔聚合结果。

## 4. 并发、失败与恢复

- 同一业务正在处理时再次拖入文件，新文件入队，当前批结束后顺序继续，不重入 OCR。
- 某个文件失败只影响所属业务；业务行保留并显示可读错误，允许重试。
- 页面切换或刷新后，前端必须从任务状态恢复正在进行的 OCR/自动审阅轮询。
- 黄灯、红灯不自动确认结论；绿灯只在全部审计门禁通过后自动收口。

## 5. 验收标准

1. 拖入文件后，目标业务行全程可见，状态从上传、OCR到自动审阅连续变化。
2. 首次上传无需点击「开始处理」；该按钮只在后续人工需求时作为「重新识别」。
3. 至少一个绿灯、一个黄灯和一个红灯夹具跑通；绿灯自动确认，黄/红均未确认。
4. 总工作台、顶部汇总和左侧阶段进度口径一致，刷新后不回灰。
5. 异常项显示业务编号、异常类型、原始单据和可定位证据；不用笼统的「未匹配」。

## 6. 测试范围

- 前端：拖放后业务行保留、状态流转、自动启动、页面恢复、红黄绿汇总与异常置顶。
- 后端：按文件集处理、仅失效受影响业务、自动结论门禁、黄/红不放行。
- 端到端：新建任务、上传抽样清单、分业务拖放文件，无人工点击处理按钮即得到逐笔灯色，并停留在总工作台异常列表。
