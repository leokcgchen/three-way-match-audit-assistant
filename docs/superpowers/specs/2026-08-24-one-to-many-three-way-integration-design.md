# 一对多三单匹配原生融合设计

**状态：** 已批准  
**日期：** 2026-08-24  
**目标工程：** `D:\抽凭—合同合规性审阅agent\.worktrees\event-driven-ui-v2`  
**能力来源：** `D:\Codex\抽凭系统设计\audit-image-lab\_review_three_way\match_engine_v1_1`

## 1. 目标与边界

将来源工程中经过夹具验证的一对多三单匹配能力，原生融合到目标工程现有的人工业务框、三单匹配、截止性测试、结论展示和底稿导出链路。

本轮只整合以下核心能力：

- 同一业务框内保留多张订单、签收/验收单和发票；
- 以订单行为锚点进行逐行绑定、分配、累计和差异判断；
- 区分部分履约、超额履约、重复分配、歧义绑定和“已齐套但仍不完整”；
- 保存可供审计师复核的来源单据、绑定依据、差额和状态轨迹；
- 在现有 React 工作台增加“本笔已齐套”控制及一对多结果展示。

本轮不引入来源工程的独立 FastAPI 服务、SQLite 任务系统、独立静态工作台、ERP 接口模拟器或整套 75 条规则契约。

## 2. 已确认的现状差异

目标工程已经具备：

- 人工 `business_group_id` 权威归属；
- 一个业务组容纳多份凭证的上传和展示能力；
- 三单字段勾稽、截止性测试、审计轨迹、结论与导出链路；
- 人工归属优先于 AI 自动分组的约束。

目标工程当前缺失：

- `merge_same_type_docs` 对同类型单据只保留完整度最高的一张；
- `find_latest_receipt_index` 只选择一张签收单参与数量比对；
- `ThreeWayMatchRequest` 只有单张订单、单张签收和单张发票；
- 缺少订单行级分配、同来源行防重和多单累计；
- 缺少“当前仅上传部分”与“本笔已齐套”的不同状态语义；
- 结果中没有逐行履约、分配依据和一对多差额轨迹。

基线复现使用来源工程 `classified_complete.json`：目标工程把三张签收单 `30 + 40 + 30` 处理成单张 `30`，而来源引擎累计为 `100`。

## 3. 方案选择

采用“原生融合”方案：在目标工程现有模块中实现一对多领域对象和聚合器，通过适配层接入当前工作流。

不直接复制整个 `match_engine` 包，原因是目标工程已有不同的 Pydantic 模型、状态口径、截止性逻辑、审计事件和导出结构。整包复制会产生两套并行规则和数据模型，增加状态冲突与维护成本。

## 4. 领域模型与模块边界

新增一个职责单一的一对多模块，建议路径：

`src/three_way_match/one_to_many.py`

该模块只负责纸面三单的一对多绑定与累计，不负责 OCR、业务分组、截止性、ERP 状态或最终底稿导出。

核心输出结构：

- `LineAllocation`：记录来源文件、来源行、角色、目标订单行、数量、金额、绑定状态、绑定等级、依据、复核状态和拒绝原因；
- `FulfillmentRow`：记录订单行、订购数量、累计签收数量、累计开票数量、累计金额、差额、参与单据、完整性声明、红黄绿状态和标志；
- `OneToManyResult`：包含全部分配记录、全部履约行和业务组摘要。

现有 `ThreeWayMatchRequest` 与单张三单 API 保持兼容。工作流内部新增一对多计算，不要求旧调用方立即改为数组请求。

## 5. 数据流

1. 当前抽样业务确定 `chain_id`，人工上传或移动凭证后写入 `business_group_id`。
2. 分组阶段继续以人工 `business_group_id` 为最高优先级，AI 不得静默覆盖。
3. 当前业务组内保留所有订单、签收/验收单、发票，不再先压缩为每类一张。
4. 一对多适配器把 OCR `fields.items[]` 转成标准行；无明细行但有头数量时，生成可追踪的合成行。
5. 以订单行作为锚点，将每张签收和发票的行分配到唯一订单行。
6. 对同一订单行累计签收数量、开票数量及可用金额，生成差额和红黄绿状态。
7. 将聚合结果写入 `fulfillment` 和 `allocations`，同时用聚合数量构造兼容的三单字段勾稽输入。
8. 截止性测试继续走现有独立链路，不把多张签收日期做求和或平均。
9. 结论页、总工作台、事件系统和底稿导出继续消费现有状态，并按需读取新增的一对多扩展字段。

## 6. 绑定规则

绑定按以下确定性顺序执行：

1. 业务框归属：不同人工业务框之间禁止自动跨组；
2. 订单号或业务引用编号精确一致；
3. 订单行号精确一致；
4. 物料编码精确一致；
5. 规格、单位与数量/金额组合形成唯一候选。

名称或语义相似只能生成候选和解释，不能单独形成自动绑定。

若出现多个同等级候选、多个冲突订单或无法唯一定位订单行，必须输出 `REQUIRES_REVIEW`，不得贪心选择。

同一来源文件的同一来源行只能成功分配一次；重复输入输出 `DUPLICATE_SOURCE_LINE`，不得重复累计。

## 7. 状态语义

默认状态表示“目前已上传的资料”，而不是审计师已经声明齐套。

| 条件 | 履约灯 | 处理含义 |
|---|---|---|
| 累计签收与累计开票均等于订单，且无绑定异常 | 绿灯 | 纸面一对多履约完整；其他审计门禁仍独立执行 |
| 已签收或已开票大于零但小于应有数量，且未声明齐套 | 黄灯 | 当前可能只是部分上传，继续补充或复核 |
| 存在无法唯一绑定的来源行 | 黄灯 | 转人工复核，不自动放行 |
| 累计签收超过订单、开票超过签收、重复分配或金额明确超额 | 红灯 | 明确纸面异常，进入人工复核 |
| 已声明“本笔已齐套”，但仍存在部分签收或部分开票 | 红灯 | `SET_CLAIMED_INCOMPLETE` |

红灯表示规则发现明确差异，不等同于已经形成审计错报。最终结论仍由现有人工复核和 ERP/截止性门禁共同决定。

## 8. 截止性隔离

一对多数量和金额累计不得改变现有截止性口径：

- 截止性继续比较控制权转移日与序时账入账日；
- 外销贸易模式继续优先使用装船/交承运人日期；
- 多张签收单存在多个日期时，保留每张来源，不求和、不平均；
- 当前兼容输入使用现有“最新有效控制权日期”规则；若存在日期冲突或业务语义不明，转人工复核；
- OCR 抽到的 `postingDate` 不能冒充序时账权威入账日。

## 9. 持久化与兼容

每个抽样业务新增布尔状态 `complete_set`，默认 `false`。状态与对应 `chain_id` 绑定，并记录更新时间；切换状态后使三单结果、结论和导出就绪状态失效并重新计算。

三单结果新增：

```json
{
  "fulfillment": {
    "complete_set": false,
    "light": "YELLOW",
    "allocations": [],
    "rows": [],
    "role_files": {
      "order": [],
      "receipt": [],
      "invoice": []
    }
  }
}
```

现有 `three_way`、`three_way_match`、`cutoff_test`、`match_result`、`quantity_roles` 和旧单张 API 字段保留。聚合完成后，`quantity_roles` 写入订单、累计签收和累计开票数量，而不是某一张代表单的数量。

## 10. UI 设计

在上传凭证页的每个业务上传行增加“本笔已齐套”复选框：

- 默认不勾选；
- 勾选前提示：该声明表示审计师认为本笔所需资料已经全部上传；
- 切换后立即持久化并重新计算当前业务的一对多三单状态；
- 操作失败时恢复原值并显示错误，不产生前后端状态漂移。

在三单结果卡展示：

- 订单、签收/验收和发票的文件数量；
- 订单数量、累计签收数量、累计开票数量；
- 数量和金额差额；
- 红黄绿状态及审计师可读原因；
- 可展开的来源文件、订单行绑定和分配依据；
- 歧义、重复和未绑定记录的人工复核提示。

总工作台沿用现有事件与红黄绿汇总，不另建第二套静态工作台。

## 11. 错误处理与安全约束

- 数量或金额无法解析时标记未测或需复核，不以零静默代替有效业务值；
- 人工业务框与单据内部订单号冲突时，保留人工归属，但明确展示编号冲突；
- 多订单无法唯一定位时不自动选择第一张；
- 无订单行但有头数量时允许生成合成行，但必须标明来源与绑定依据；
- 同一文件重复上传或同一来源行重复出现时防止重复累计；
- 一对多绿灯不能覆盖现有 P0、ERP、截止性或人工确认门禁。
