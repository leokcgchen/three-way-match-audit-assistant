# 可解释动态字段解析与跨单据实体勾稽设计

## 1. 目标

系统应根据每笔业务实际上传的单据动态发现字段、理解字段语义并建立跨单据连接，同时保证每个提取值、连接关系和判断结果都能回到原件证据并由确定性步骤复算。

本设计解决以下问题：

- 不同客户、ERP、贸易模式和单据类型的字段并不固定，预设字段表无法覆盖全部情况；
- 当前页面把“应完全一致”“可复算”“仅看时序”“单据专有”混在同一张相等性表中，容易制造假异常；
- 大模型能够发现动态字段和理解复杂版面，但不能成为无法复核的黑箱；
- 多品项、一对多交付、分批开票需要明细级连接和汇总勾稽，不能只比较单据总值。

## 2. 不变边界

1. 抽样清单仍是审阅总体的唯一边界；字段发现和实体解析不得新增业务。
2. 文件名、目录名不能作为字段语义、单据类型或一致性结论的证据。
3. 每项字段主张必须具有 `文件 + 页码 + 字符范围或坐标 + 原文`；没有原件锚点的字段无效。
4. 大模型可以提出字段、语义和连接，但不能脱离证据直接改变规则结论或给出最终审计意见。
5. 金额、数量、日期、编号的最终比较和复算由代码执行；模型不得以自然语言覆盖确定性结果。
6. 存在强反证时不得用多个弱相似项“投票通过”。

## 3. 方案选择

采用“动态字段规划 + 实体解析图 + 确定性执行”的混合方案：

- 规则引擎负责精确匹配、标准化、数学复算、日期顺序和已登记映射；
- 大模型负责字段发现、版面理解、语义归一、字段角色识别和候选连接；
- 审计师负责证据不足、含义歧义和待建立映射的事项；
- 页面自然语言解释由结构化解释包生成，不把模型自由文本当作唯一理由。

不采用纯固定字段方案，因为无法适配新贸易场景；不采用完全自由的大模型方案，因为输出不稳定且不可独立复核。

## 4. 处理架构

### 4.1 页面级证据采集

每份文件先按页面处理。系统保留页面文字、表格行列、显式标签—值、无标签数值和未能归义的候选片段；不因字段不在预设字典中而丢弃。OCR、PDF文字层或视觉模型输出候选字段，但字段必须绑定原件位置。候选字段不立即进入三单比较。

输出 `field_evidence_node`：

```json
{
  "evidence_id": "ev-...",
  "document_id": "doc-...",
  "document_role": "order",
  "page": 1,
  "label_text": "规格型号",
  "raw_value": "SM-130",
  "char_start": 1280,
  "char_end": 1286,
  "bbox": [0.31, 0.42, 0.46, 0.47],
  "source": "pdf_text|ocr|vision",
  "extractor": "rule|model",
  "extractor_version": "...",
  "confidence": 0.97
}
```

同一字段可有多个候选值。候选值之间发生冲突时保留全部候选，不静默覆盖。

### 4.2 动态语义归一

模型将原始字段映射为业务概念，例如：

- `收货单位`、`购买方名称`、`客户名称` → `buyer_legal_entity`；
- `货物名称+规格型号`、`商品或劳务名称` → `goods_identity`；
- `价税合计`、`含税总额` → `gross_amount`；
- `验收完成时间` → `control_transfer_event_time` 候选。

模型输出必须包含：目标概念、字段角色、适用单据、原件证据ID、映射理由、可能反证和置信度。模型不能生成原件中不存在的字段值。

### 4.3 跨单据实体解析图

字段节点之间建立 `resolution_edge`：

```json
{
  "edge_id": "edge-...",
  "concept": "goods_identity",
  "left_evidence_ids": ["ev-order-name"],
  "right_evidence_ids": ["ev-receipt-name", "ev-receipt-model"],
  "relation_type": "SEMANTIC_EQUIVALENT",
  "decision_owner": "rule|model|human",
  "status": "CONFIRMED|CANDIDATE|MAPPING_REQUIRED|CONFLICT|REJECTED",
  "transformations": ["split_name_and_model", "normalize_space_case"],
  "confirmed_facts": ["品名一致", "型号完全一致"],
  "counter_evidence": [],
  "reason_code": "NAME_MODEL_SPLIT_EQUIVALENT"
}
```

连接类型包括：

- `EXACT_EQUAL`：原值完全一致；
- `NORMALIZED_EQUAL`：经过大小写、空格、标点、法定后缀等受控标准化后一致；
- `REFERENCE_EQUAL`：订单号、发票号等明确引用一致；
- `DERIVED_EQUAL`：通过税额、单价、数量或汇总公式复算一致；
- `SEMANTIC_EQUIVALENT`：字段拆分或同义表达后实质一致；
- `TEMPORAL_RELATION`：只判断事件先后和期间，不要求日期相等；
- `MAPPING_REQUIRED`：需要系统间主数据映射；
- `DOCUMENT_SPECIFIC`：单据专有字段，不参与三单一致性；
- `CONFLICT`：存在无法消解的强反证。

### 4.4 动态比较计划

系统在识别单据类型和候选字段后，为本笔业务生成 `comparison_plan`，不再在上传前固定所有比较行。每个比较项包含：

- 展示名称与标准概念；
- 适用单据角色；
- 比较方式；
- 使用的证据节点；
- 标准化或复算公式；
- 是否影响三单结论；
- 缺失时是“缺证据”还是“不适用”；
- 自动确认门槛与人工问题。

比较项分为五个展示域：

1. 一致性字段；
2. 复算与汇总字段；
3. 时序和业务过程；
4. 单据专有信息；
5. 待解释、待映射或冲突事项。

## 5. 自动确认灵敏度

### 5.1 规则自动确认

以下结果在证据有效且不存在冲突时自动确认：

- 精确编号匹配；
- 受控标准化后的主体、地址、单位或币种匹配；
- 金额、税额、单价、数量公式复算；
- 一对多汇总勾稽；
- 日期大小、事件先后和报告期判断；
- 已有、有效且版本明确的主数据映射。

### 5.2 模型语义连接自动确认

模型提出的语义连接只有同时满足以下条件才可自动确认为 `SEMANTIC_EQUIVALENT`：

1. 至少两个独立证据维度支持；
2. 每个证据均可定位到原件；
3. 没有强反证；
4. 连接没有改变金额、数量、编号或日期的确定性结果；
5. 模型输出符合受控JSON结构并通过代码校验。

“独立证据”指不同语义维度，例如名称与型号、名称与税号、金额与数量公式。重复描述同一个字段、同一模型输出两次或多个相似词不构成独立证据。

### 5.3 必须人工确认

- 只有一个语义证据；
- 两个不同系统编码缺少映射表；
- 字段角色不清，例如收货方是否等于合同买方；
- 贸易条款对控制权时点存在多种合理解释；
- OCR候选之间冲突；
- 强字段出现反证；
- 模型置信度不足或证据定位失败。

### 5.4 结果优先级

同一比较概念出现多个状态时，按以下顺序收口：

1. 强反证或确定性复算失败 → `CONFLICT/FAIL`；
2. 影响三单结论的必要证据缺失 → `MISSING_EVIDENCE/REVIEW`；
3. 主数据映射缺失但核心交易事实已确认 → `PASS_WITH_WARNING`；
4. 规则确认或满足门槛的语义确认，且无反证 → `PASS`；
5. 不适用或单据专有字段 → 不进入三单状态计算。

模型置信度只决定是否进入人工队列，不能覆盖上述优先级。

## 6. 多品项和一对多处理

单据明细先形成行级节点，再匹配和汇总。匹配优先级为：

1. 物料编码或唯一型号；
2. 规格型号；
3. 标准化品名；
4. 数量与单位；
5. 单价和行金额；
6. 批次、箱号或其他辅助信息。

允许一对一、一对多、多对一、分批交付和分批开票。系统先建立明细连接，再按连接组分别汇总数量与金额；不得因为单份签收单或发票金额不等于订单总额而拒绝归类或直接判错。

每个汇总必须保存参与计算的行、原始值、单位换算、算式、容差和结果。

## 7. 页面设计

### 7.1 一致性与复算

横向展示抽样清单、订单、合同、签收/发货、发票。每行状态使用：

- 完全一致；
- 标准化一致；
- 实质一致；
- 复算一致；
- 待映射；
- 缺少证据；
- 不一致；
- 不适用。

点击任一值定位原件。点击状态打开“为什么”抽屉，展示证据节点、转换步骤、公式、支持证据和反证。

### 7.2 时序与业务过程

使用事件时间线而不是相等性表，展示订单、计划交付、发货、到货、验收、控制权转移、开票和入账事件。系统说明比较基准、期间内外、先后关系和偏差天数。

### 7.3 单据专有信息

展示批次、承运单位、车牌、银行账号、开票人、检验项目等。其他单据不存在该字段时显示“不适用”，不形成缺字段或三单异常。

### 7.4 待解释事项

集中展示映射缺口、语义歧义和强反证。审计师可以确认、拒绝、补充映射证据或请求补件。人工动作写入审计日志，不直接改写原始提取值。

## 8. 3962金标准样本

3962业务作为首个验收样本，预期如下。

### 8.1 一致性与复算通过

- 关联订单号 `SO-251209-7214`；
- 卖方名称和地址；
- 买方/收货方名称和地址；
- 货品“伺服电机”与型号 `SM-130`；
- 数量20台；
- 未税金额100,000元、税额13,000元、价税合计113,000元；
- 含税单价5,650元与未税单价5,000元通过13%税率复算一致。

### 8.2 时序通过

- 计划交期：2026-01-02；
- 实际验收并完成控制权转移：2026-01-02 09:40；
- 开票：2026-01-02 14:50；
- 结论展示为验收先于开票、时序合理，不把这些日期要求为同值。

### 8.3 客户编码待映射

- 销售订单：`KH-330212-0142`；
- 签收验收单：`KH-NB-0062`；
- 发票：无客户编码。

客户名称、地址和税号支持同一主体，但不同系统编码缺少映射证据。因此：

- 交易主体连接可以确认；
- 客户编码关系为 `MAPPING_REQUIRED`；
- 三单状态为“通过，但有辅助主数据预警”；
- 截止性测试为“通过”；
- 客户编码差异不能被模型自动抹平。

## 9. 错误处理与审计日志

- OCR、模型或规则的每次运行记录版本、输入证据哈希、输出、耗时和错误；
- 模型返回无效JSON、引用不存在证据或生成原文不存在的值时，该次输出整体降级为待复核；
- 新一轮识别不得覆盖旧证据，使用版本化结果并记录当前有效版本；
- 规则、映射和人工确认均记录操作者、时间、理由和影响范围；
- 已确认的客户编码映射必须区分任务级、被审计单位级和全局级，不默认跨客户复用。

## 10. 性能与调用策略

- PDF文字层和规则提取优先；只把规则无法归义的页面或区域交给视觉模型；
- 单据字段发现可并行，但跨单据实体解析必须在本笔业务文件集合齐备后执行；
- 已有证据节点按文件哈希缓存；字段规划变化只重跑规划和勾稽，不重复OCR；
- 模型输出使用受控字段数量和文本窗口，避免整本PDF反复调用。

## 11. 验收与反例

必须覆盖：

- 3962完整金标准；
- 同名客户但税号不同，必须冲突；
- 客户编码不同且无映射，必须待解释；
- 商品名称拆分、型号一致，可语义确认；
- 名称相似但型号不同，不得通过；
- 含税与未税单价可复算；
- 金额公式不成立，必须失败；
- 多品项顺序变化仍正确匹配；
- 一对多签收数量加总一致；
- 一对多加总不足或超量，必须异常；
- 单据日期不同不产生“一致性失败”；
- 承运人、车牌、银行账号缺失于其他单据时显示不适用；
- 模型无证据、证据重复、证据位置无效时不能自动确认；
- 两个弱相似项不能覆盖一个强反证；
- 模型服务不可用时规则路径仍可运行，语义项进入待复核。

## 12. 迁移策略

保留现有字段值和字段编辑功能，新增证据节点、连接图和动态比较计划。旧任务没有证据位置时标记为“历史提取，待定位”，不能伪装成已定位证据。前后端现有固定字段清单逐步降级为兜底模板，不再成为唯一比较来源。

三单匹配与截止性测试继续保持独立：三单匹配使用一致性、实质一致和复算连接；截止性使用事件、日期及控制权规则，不把日期相等性混入三单结论。
