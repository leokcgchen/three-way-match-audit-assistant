# 受控审阅流水线与模块边界规范

## 目标

所有收入抽凭底稿复用同一条受控主链：每个模块独立封装、逐步放行、每一步可解释且可追溯。任何上游证据、字段、分组或人工决定改变时，系统自动使后续模块失效；不允许跳步，也不允许以模型输出代替审计师确认。

```mermaid
flowchart LR
  A[上传与OCR] --> B[字段库绑定]
  B --> C[人工确认字段]
  C --> D[业务组确认]
  D --> E[三单字段一致性]
  E --> F[人工确认三单]
  F --> G[截止性测试]
  G --> H[人工确认截止性]
  H --> I[底稿生成与复核]
```

## 模块契约

| 顺序 | 模块 | 输入 | 产出 | 人工门禁 | 下游失效条件 |
|---:|---|---|---|---|---|
| 1 | `ocr_ingest` | 原始PDF/图片/Excel | OCR文本、页码、坐标、原始字段候选 | 无；仅处理完成 | 重传、重识别 |
| 2 | `field_binding` | OCR结果、字段库 | 字段—来源映射、`_field_meta` | 审计师确认每一业务组字段 | 字段编辑、重绑、圈画、重分类 |
| 3 | `business_grouping` | 已确认的关键标识字段 | `BusinessGroup`、强/弱依据、状态 | 审计师确认组或拖拽调整 | 移组、合并、拆分、关键标识修改 |
| 4 | `three_way_match` | 已确认业务组及组内已接受字段 | 单据捆绑、字段一致性、决策轨迹 | 审计师确认通过或进入异常处理 | 组变更、字段变更 |
| 5 | `cutoff_test` | 已确认三单、期间参数、控制权/签收/入账证据 | 截止性结果、日期依据、偏差说明 | 审计师确认结果 | 期间、字段、三单结果变更 |
| 6 | `workpaper_export` | 已确认的前五步及异常处置 | 带 `group_id` 的底稿、复核轨迹 | Gate5复核 | 任一上游失效 |

## 显示给审计师的决策轨迹

每个模块结果都必须显示如下结构，替代所谓“模型思维过程”：

```json
{
  "stage": "three_way_match",
  "status": "PASS | FAIL | NEEDS_REVIEW | BLOCKED | NOT_TESTED",
  "facts": [{"source_document":"...","page":0,"field":"totalAmount","value":"...","excerpt":"..."}],
  "rules_applied": [{"rule_id":"TW-FIELD-001","description":"同组已接受字段的金额口径比较"}],
  "candidates": [],
  "conflicts": [],
  "human_decision": {"status":"PENDING | CONFIRMED | REJECTED","actor":"...","at":"...","reason":"..."},
  "downstream_effect":"允许截止性测试 | 阻断并返回字段校对"
}
```

不得展示隐藏推理链；不得把LLM理由当作事实。字段、日期、金额、业务号等材料性结论必须能定位到原件。

## 门禁状态机

1. OCR完成前，字段绑定为 `BLOCKED`。
2. 字段绑定未由人工确认前，业务组只能是系统预分组，不能执行或确认三单匹配。
3. 任何 `NEEDS_REVIEW` 或 `CONFLICT` 业务组未处置前，三单匹配为 `BLOCKED`。
4. 三单字段一致性未人工确认，截止性测试为 `BLOCKED`。
5. 截止性测试为 `FAIL` 或 `NEEDS_REVIEW` 时，禁止直接导出正式底稿；只能进入异常处置或经授权复核确认。
6. 任一步被编辑后，自动撤销该步及下游确认；保留历史审计轨迹，不覆盖旧记录。

## AI权限（P3）

AI仅可在明确的模块内：

- 从OCR文本/版面生成字段候选；
- 为字段候选、业务组弱特征和异常提供**带来源的说明**；
- 在已确认的 `group_id` 上下文内生成语义审阅候选。

AI不得：自动接受字段、填补没有原文的值、确认业务分组、确认三单/截止性通过、修改底稿结论、跨业务组读取上下文、写入生产状态。所有写入均由规则引擎或人工确认API完成。

## API与UI封装要求

- 每个模块提供 `run`、`get_result`、`confirm`、`invalidate` 四类接口；UI不直接修改下游状态。
- `confirm` 必须校验上一步状态、材料性异常、待决AI候选与操作者理由，并写入HITL日志。
- UI采用“当前阶段一张主卡 + 已完成阶段可折叠摘要 + 后续阶段锁定”的布局；顶部仅保留紧凑进度条，不固定占用大量高度。
- 业务组页面只负责分组确认；三单页只负责捆绑与字段一致性；截止页只负责期间判断；避免重复按钮与混合FAIL原因。

### 已落实的合并式三单匹配工作台

左侧入口为“**三单匹配（分组＋字段）**”，而不是两个分散菜单：

1. 上半部分是“业务分组与人工复核”卷轴，逐组展示强主键、规则/AI说明、字段待核提示、单据标签与拖拽调整；`确认本组分组` 只确认业务捆绑。
2. 当所有业务组确认后，上半部分自动折叠为一条可展开摘要；审计师需要复看证据、拖拽记录或规则时再点击展开。
3. 下半部分“组内字段一致性与原文取证”保持展开，复用字段矩阵、原件高亮、圈画、人工修改和字段重绑定；它不允许修改分组。
4. 截止性测试仍为独立左侧入口及独立页面，因为其证据、期间参数、偏差解释和复核范围明显更大。

分组确认接口为 `POST /jobs/{job_id}/hitl/business-groups/confirm`。拖拽移组接口会清空 `business_group_confirmations` 并记录HITL，防止旧分组确认被复用。

## 验收用例

| 场景 | 预期 |
|---|---|
| OCR把金额映射错字段 | 字段矩阵高亮，未确认前分组/三单锁定 |
| 两个业务组客户相同金额相同但无强主键 | 不自动合并，状态 `NEEDS_REVIEW` |
| 同一业务组单据已绑定但金额不一致 | 分组保持匹配，三单字段一致性FAIL并说明字段原因 |
| 字段确认后人工移动单据 | 撤销该组及下游三单/截止确认，记录移组轨迹 |
| 截止性失败 | 底稿正式导出锁定，异常处置可见证据和规则 |
